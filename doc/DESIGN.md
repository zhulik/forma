# forma — design concepts

forma lets you build interactive UIs in **Go only**. You describe screens as typed, composable components; a fixed **React + shadcn/ui** layer turns that description into DOM updates. The design goal is the best practical DSL for UI authoring with **as little hassle as possible**—especially for agents, who should output reviewable Go instead of HTML/CSS/JS.

This document captures the architecture and product decisions from the original design exploration (high-level UI, shadcn, GopherJS vs Wasm, recursive tree rendering, codegen, state model). Implementation details evolve in OpenSpec changes; this is the conceptual anchor.

---

## Motivation

- **HTML/CSS/JS are the wrong authoring surface** for many teams: verbose, inconsistent, and hard to review when generated by LLMs.
- **Semantic widgets beat structural nodes**: authors think in `Button`, `DataTable`, `Dialog`—not div stacks and class strings.
- **Go as the single source of truth** for layout, state, and business logic keeps apps predictable and testable in one language.
- **Reuse the React ecosystem** for visuals and third-party widgets (maps, payments, charts) without forcing authors to write React.

---

## Stack choice

| Layer | Choice | Why |
|--------|--------|-----|
| Authoring | Go | Strong types, familiar backend idioms, good for agents |
| Browser compilation | **GopherJS** (v1) | Go structs and funcs map to JS objects/callbacks without a Wasm JSON bridge on every update |
| Visual components | **React 18 + shadcn/ui** | shadcn is copy-paste TSX (great for codegen); huge third-party React catalog |
| Styling | Tailwind (via shadcn) | Authors rarely touch CSS; optional `Class` escape hatch |
| Wasm (Go `syscall/js`) | **Not v1** | Heavier payloads, serialization cost for full UI trees; revisited only if GopherJS limits bite |

Alternatives considered (Solid/Svelte signals, HTMX/HTML-over-the-wire, Franken UI) trade away **transparent React third-party components**. forma standardizes on React as a **dumb renderer** so Stripe, Leaflet, data grids, etc. stay one registry entry away.

## System architecture

Three cooperating parts:

```
┌─────────────────────────────────────────────────────────┐
│  Go application (GopherJS → JS)                          │
│  • App state (structs, vars)                             │
│  • ui.Mount / ui.Refresh                               │
│  • Component tree via Render(ctx) → Node                 │
└───────────────────────────┬─────────────────────────────┘
                            │ structs, func callbacks, tree
                            ▼
┌─────────────────────────────────────────────────────────┐
│  JavaScript host (write once)                            │
│  • ComponentRegistry: "Button" → shadcn Button           │
│  • Recursive Widget renderer                             │
│  • Event sanitization (DOM → plain data)                 │
│  • Optional islands for heavy 3rd-party React widgets  │
└───────────────────────────┬─────────────────────────────┘
                            │ React reconciliation
                            ▼
                     Browser DOM
```

**Code generator (build time):** Node script (e.g. ts-morph) reads `components/ui/*.tsx`, emits `ui/*.gen.go` with typed fields and `Render` glue. Regenerating after shadcn updates keeps Go APIs in sync without hand-maintaining hundreds of props.

## Authoring model (DSL)

The north-star example is [`main.go`](../main.go): a todo app with no HTML.

### Core APIs

- **`ui.Mount(elementID, root Component)`** — attach the app to a DOM mount point once.
- **`ui.Refresh()`** — after mutating app state, rebuild the tree and push it to the host.
- **`Component` interface** — `Render(ctx context.Context) *Node`.

### Composition

- **Struct literals + `.With(...)`** — children as components or strings; value receivers keep trees immutable per build.
- **Layout primitives** — `Row`, `Column`, `Container`, `Card`, … express structure without HTML tag names.
- **Generated shadcn types** — `Button`, `Input`, `Checkbox`, … with typed props (`Variant`, `Size`, …).
- **Escape hatches** — `Class`, `Style`, `Attrs` on `BaseComponent` for the rare Tailwind tweak; not the default path.

### Custom components

- **In Go:** functions or structs that return `Component` by composing existing nodes (e.g. `UserCard(user User) ui.Component`).
- **In JS:** thin `.tsx` wrappers for third-party React libs, registered in `ComponentRegistry`, exposed to Go via a generated or hand-written struct.

### Events and `context.Context`

- Handlers are Go functions; **React never passes SyntheticEvent into Go**.
- The host extracts primitive payloads (string, bool, `map[string]any`) and invokes the Go callback.
- **`context.Context`** on handlers supports cancellation: when a subtree unmounts, work started from that subtree should stop (HTTP, timers, goroutines). Exact scoping is specified in OpenSpec (`ui-dsl` / runtime changes).

### State and reactivity (Elm-style)

1. Application state lives in **Go** (structs, slices, maps)—not in React `useState` for domain data.
2. UI is a **pure function of state**: `Refresh` rebuilds a lightweight tree from current state.
3. React **diffs** the new tree against its virtual DOM; the browser is not blindly repainted.

**Text inputs:** typing every keystroke through Go + full refresh can cause focus/cursor issues. The spec allows **controlled hybrid** behavior: React may hold ephemeral input state locally; Go receives updates on `onBlur`, submit, or debounced `onChange`—documented per component in user guide.

**Lists:** stable **`Key`** (or equivalent) on repeated nodes so React reconciles lists correctly.

### Async

- Use normal **goroutines** and **`net/http`** (GopherJS maps them to async JS).
- After async work, mutate Go state and call **`Refresh()`** (often from the goroutine, respecting `ctx` cancellation).

## Code generation

shadcn installs **source** `.tsx` into the repo, which makes AST-based generation reliable.

| TypeScript | Go (typical) |
|------------|----------------|
| `string`, `boolean`, `number` | `string`, `bool`, `float64` |
| Union literals `"default" \| "ghost"` | `string` + optional `const` block |
| `React.ReactNode` | children via `.With(...)` / nested `Component` |
| `(e: MouseEvent) => void` | `func(ctx context.Context)` or `func(ctx context.Context, data map[string]any)` |
| Complex 3rd-party props | narrow in JS wrapper; Go sees clean fields |

Generated files are **`*.gen.go`**; manual edits live in separate files or documented extension points.

## Third-party React modules

Pattern:

1. Add a small **JS wrapper** that owns refs, imperative APIs, and event sanitization.
2. Register in **`ComponentRegistry`** under a stable type string (e.g. `"StripeCard"`).
3. Expose **Go struct** (generated or hand-written) with props + callbacks.

Go stays free of DOM types; the wrapper converts vendor events to plain data before calling Go.

## How users work with forma

### Day-to-day flow

1. **Create a Go module** that imports `github.com/zhulik/forma/ui`.
2. **Define app state** as ordinary Go types.
3. **Implement `func MyApp() ui.Component`** (or equivalent root) using layout + shadcn components.
4. **`ui.Mount("app-root", MyApp())`** from `main`.
5. On user actions or async completion: **update state → `ui.Refresh()`**.

### Adding shadcn components

1. Install component via shadcn CLI into the host app's `components/ui/`.
2. Register the component in the **JS registry**.
3. Run **codegen** to emit/update `ui/<name>.gen.go`.
4. Use the new type in Go immediately.

### Desktop (later)

Same Go + host bundle, served inside a **native system webview** (not Electron). Web path comes first; desktop is packaging, not a second UI model.

## Non-goals (initial releases)

- **Server-side rendering** as a first-class story (possible later via V8/hydration or separate SSR track—not v1).
- **Replacing React** with Solid/Svelte for the core registry while keeping shadcn parity.
- **Authoring HTML/CSS/JS** as the primary path.
- **Hand-writing every shadcn prop** without codegen.
- **Full shadcn catalog** before the DSL and runtime loops are proven on a subset (button, input, layout, table, dialog, …).
